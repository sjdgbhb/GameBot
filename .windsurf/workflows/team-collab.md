# GameBot 团队协作模式

## 团队成员

| 角色 | 基座模型 | 职责 | 专长 |
|------|---------|------|------|
| **Dev** — 开发工程师 | GLM-5.2 High | 功能实现、架构设计、Bug 修复 | 逻辑推理、复杂工程实现、边界把控 |
| **QA** — 测试工程师 | SWE-1.7 Max | 测试编写、边界发现、代码审查、验证命令 | 代码生成、测试自动化、长上下文理解 |

## 模型切换指引

Windsurf 目前不支持自动切换模型，需手动操作：

```
聊天面板顶部 → 点击模型名称 → 选择目标模型
```

**每个 Dev / QA 阶段/轮次开始前，你必须先主动使用 **cascade** 在对话中询问用户当前模型，确认已切换到对应角色所需的基座模型后，才能继续执行。**
**未得到用户通过 **cascade** 明确确认（如“已切换”/“确认继续”）前，必须暂停等待，禁止自行进入下一阶段。**

---

## 协作流程

> 🛑 **关键规则：阶段间硬停止并主动 cascade 询问**
> 每个阶段完成后，当前 agent 必须**立即停止工作**，输出阶段完成汇报，然后**主动使用 **cascade** 在对话中询问用户当前模型是否已切换**。
> **禁止跨阶段连续执行**——即使下一个阶段的步骤已在 workflow 中描述，也必须等用户通过 **cascade** 明确确认后，由新一轮对话继续。
> 这是为了确保 Dev 不越界写测试、QA 不越界改业务代码。

### 阶段一：需求评审（Dev 先评审 → QA 后评审，支持多轮迭代）

> ⚠️ **本阶段可能多轮迭代，Dev 和 QA 必须使用不同模型**
> Dev 使用 GLM-5.2 High，QA 使用 SWE-1.7 Max，**严禁 Dev、QA 在同一阶段使用同一基座模型**。
> 每轮/每步开始前，你必须先使用 **cascade** 在对话中主动询问用户当前模型，确认已切换到对应角色的基座模型并回复确认后，才能继续；未确认前禁止继续。
> **每轮评审必须输出/更新评审报告到 `docs/review_reports/YYYY-MM-DD_<主题>.md`**，下一轮 Dev/QA 在继续前必须阅读该报告。

#### 步骤 1-A：Dev 初评（GLM-5.2 High）

> ⚠️ **当前应为 GLM-5.2 High**
> 阶段开始前，你必须先使用 **cascade** 在对话中主动询问用户当前模型。只有在用户明确回复已切换到 **GLM-5.2 High** 并确认继续后，才能继续。

1. 理解用户需求，明确功能目标和涉及模块
2. 阅读相关配置文件、业务代码和同类任务实现
3. Dev 输出实现方案：
   - 需要创建/修改的文件清单
   - 核心函数/类设计
   - 涉及的配置文件
4. **输出/更新评审报告**到 `docs/review_reports/YYYY-MM-DD_<主题>.md`，按「需求评审报告格式」写入实现方案

**需求评审报告格式**：
```
# 需求评审报告 — <主题>
> 日期：YYYY-MM-DD

## [Dev] 需求评审 — 实现方案
- 功能目标：...
- 涉及模块：...
- 需要创建/修改的文件清单：
  - `path/to/file.py` — 新增/修改 xxx
- 核心函数/类设计：...
- 涉及的配置文件：...
```

> 🛑 **步骤 1-A 完成 → 硬停止并主动 cascade 询问**
> 输出上述 Dev 评审结果后，立即停止工作。主动使用 **cascade** 在对话中询问用户：
> "Dev 评审已完成，评审报告已写入 `docs/review_reports/YYYY-MM-DD_<主题>.md`。接下来进入 QA 评审，需要切换到 SWE-1.7 Max。请确认后继续。"
> 只有在用户明确回复已切换到 **SWE-1.7 Max** 并确认继续后，才能继续。**不要自行进入步骤 1-B**。

#### 步骤 1-B：QA 初评（SWE-1.7 Max）

> ⚠️ **当前应为 SWE-1.7 Max**
> 阶段开始前，你必须先使用 **cascade** 在对话中主动询问用户当前模型。只有在用户明确回复已切换到 **SWE-1.7 Max** 并确认继续后，才能继续。
> 切换方法：聊天面板顶部 → 选择 SWE-1.7 Max

1. **阅读 `docs/review_reports/YYYY-MM-DD_<主题>.md` 中的 Dev 实现方案**
2. QA 输出测试方案：
   - 需要覆盖的测试点
   - 预期的边界条件和异常场景
   - 需要的测试数据
3. QA 对 Dev 的实现方案提出补充或质疑（如有）
4. **在评审报告中追加/更新 QA 评审意见和测试方案**

**QA 初评追加格式**（追加到评审报告）：
```
## [QA] 需求评审 — 测试方案
- 需要覆盖的测试点：...
- 预期的边界条件和异常场景：...
- 需要的测试数据：...
- 对 Dev 实现方案的意见：无 / 列出补充建议
### 待确认/待修改项
- [ ] 项 1：...
```

> 🛑 **步骤 1-B 完成 → 硬停止并主动 cascade 询问**
> 输出上述 QA 评审结果后，立即停止工作。主动使用 **cascade** 在对话中告知用户评审结论：
> - 如果 QA 无补充/质疑：告知用户 "QA 评审已通过。接下来进入阶段二（开发实现），需要切换到 GLM-5.2 High。请确认后继续。"
> - 如果 QA 有需 Dev 修改的补充/质疑：告知用户 "QA 评审有补充意见，需要 Dev 修改后重新评审。需要切换到 GLM-5.2 High。请确认后继续。"
> 只有在用户明确回复确认后，才能继续。**不要自行进入下一阶段/循环**。

#### 阶段一迭代循环（未达成共识时 Dev ↔ QA）

> ⚠️ **循环直到达成共识**
> - Dev 修改 → GLM-5.2 High
> - QA 复核 → SWE-1.7 Max
> **严禁 Dev、QA 在同一轮循环中使用同一基座模型。**
> 每轮开始前，必须先使用 **cascade** 在对话中询问用户确认当前模型。

```
循环直到共识达成：
  1. [Dev] 阅读 `docs/review_reports/YYYY-MM-DD_<主题>.md` 中的 QA 意见
  2. [Dev] 修改实现方案并更新评审报告（仅修改实现方案，不修改 QA 意见）
  3. [Dev] 输出 [Dev] 修改说明到评审报告
  4. [Dev] 停止并主动使用 cascade 询问用户切换到 SWE-1.7 Max
  5. [QA] 阅读更新后的评审报告
  6. [QA] 复核并更新 QA 意见/测试方案
  7. [QA] 输出复核结论到评审报告
  8. [QA] 停止并主动使用 cascade 询问用户：若通过则进入阶段二（切换 GLM-5.2 High），若未通过则继续下一轮（切换 GLM-5.2 High）
```

**Dev 修改追加格式**（追加到评审报告）：
```
### [Dev] 方案修改
- 修改项：...
- 影响范围：...
```

**QA 复核追加格式**（追加到评审报告）：
```
### [QA] 复核结论
- 通过 / 不通过
- 原因：...
```

> 🛑 **阶段一完成 → 硬停止并主动 cascade 询问**
> 达成共识后，立即停止工作。主动使用 **cascade** 在对话中询问用户：
> "阶段一（需求评审）已完成。评审报告已最终确认在 `docs/review_reports/YYYY-MM-DD_<主题>.md`。接下来进入阶段二（开发实现），需要切换到 GLM-5.2 High。请确认后继续。"
> 只有在用户明确回复确认后，才能继续。**不要自行进入阶段二**。

---

### 阶段二：开发实现（Dev 主导）

> ⚠️ **Dev 主导，当前应为 GLM-5.2 High**
> 阶段开始前，你必须先使用 **cascade** 在对话中主动询问用户当前模型。只有在用户明确回复已切换到 **GLM-5.2 High** 并确认继续后，才能继续。

1. **查阅 `docs/test_reports/` 下的 QA 测试报告**，优先处理 P0/P1 待修复项
2. 阅读相关配置文件和现有代码
3. 按实现方案编写代码，遵循 `.windsurfrules` 规范：
   - 配置值从 TOML 读取，不硬编码
   - 注意双 Python 环境隔离（3.12 主环境 / 3.8 大漠环境）
   - import 语句在文件顶部
4. 确保代码可立即运行
5. 输出变更摘要，并更新测试报告中对应待修复项的状态

**输出格式**：
```
## [Dev] 开发完成
### 变更文件
- `path/to/file.py` — 新增/修改了 xxx
### 变更摘要
- 新增函数：func_a(), func_b()
- 修改逻辑：xxx
### 自测情况
- 已确认 import 完整
- 已确认配置从 TOML 读取
### 变更日志
- 已写入 `docs/change_logs/YYYY-MM-DD_xxx.md`
```

> 🛑 **阶段二完成 → 硬停止并主动 cascade 询问**
> 输出上述开发完成汇报后，立即停止工作。**禁止编写任何测试代码**（那是 QA 的工作）。
> 主动使用 **cascade** 在对话中告知用户：
> "阶段二（开发实现）已完成。接下来进入阶段三（测试编写），需要切换到 SWE-1.7 Max。请确认后继续。"
> 并询问用户是否已切换并确认，**只有在用户明确回复确认后，才能继续**。未得到确认前不得继续，**不要自行进入阶段三**。

---

### 阶段三：测试编写（QA 主导）

> ⚠️ **QA 主导，当前应为 SWE-1.7 Max**
> 阶段开始前，你必须先使用 **cascade** 在对话中主动询问用户当前模型。只有在用户明确回复已切换到 **SWE-1.7 Max** 并确认继续后，才能继续。
> 切换方法：聊天面板顶部 → 选择 SWE-1.7 Max

1. 阅读 `docs/change_logs/` 下的最新变更日志，了解本次 Dev 变更涉及的文件、函数/类、配置及影响范围；根据变更摘要编写测试代码
2. 遵循项目现有测试风格（参考 `tests/unit/` 下的测试）
3. 覆盖维度：
   - 正常路径（happy path）
   - 边界条件（空值、极值、临界状态）
   - 异常场景（错误输入、依赖缺失）
   - 配置继承机制（如涉及配置系统）
4. 运行测试验证
5. **输出测试报告到 `docs/test_reports/`**（文件名 `YYYY-MM-DD_<主题>.md`）
   - 报告格式见 `test-engineer.md` 中的「测试报告格式」
   - Dev 通过报告了解待修复项

**输出格式**：
```
## [QA] 测试完成
### 变更日志
- 已阅读 `docs/change_logs/YYYY-MM-DD_xxx.md`，确认本次测试范围、重点和回归项
### 测试文件
- `tests/unit/test_xxx.py` — 新增 N 个测试用例
### 测试覆盖
- test_func_a_normal — 正常路径
- test_func_a_edge_case — 边界条件
- test_func_a_error — 异常场景
### 运行结果
- 通过: N | 失败: M | 跳过: 0
### 测试报告
- 已输出到 `docs/test_reports/YYYY-MM-DD_xxx.md`
```

> 🛑 **阶段三完成 → 硬停止并主动 cascade 询问**
> 输出上述测试完成汇报后，立即停止工作。
> 主动使用 **cascade** 在对话中告知用户下阶段安排，并询问是否已切换并确认模型：
> - 如果测试全部通过：告知用户 "阶段三（测试编写）已完成，全部通过。接下来进入阶段五（交叉审查），请确认后继续。"（跳过阶段四）
> - 如果有测试失败：告知用户 "阶段三（测试编写）已完成，有 M 项失败。接下来进入阶段四（Bug 修复循环），需要切换到 GLM-5.2 High。请确认后继续。"
> **只有在用户明确回复确认后，才能继续**。未得到确认前不得继续，**不要自行进入下一阶段**。

---

### 阶段四：Bug 修复循环（Dev ↔ QA）

> ⚠️ **根据当前角色切换模型，每次切换前必须使用 cascade 询问用户确认**
> - 修复代码 → GLM-5.2 High（Dev）
> - 重跑测试 → SWE-1.7 Max（QA）
>
> **严禁 Dev、QA 在同一轮循环中使用同一基座模型。**

如果阶段三有测试失败：

```
循环直到全部通过：
  1. [QA] 报告失败详情到 `docs/test_reports/`（失败用例、错误信息、复现步骤）
  2. [Dev] 查阅测试报告，分析根因，修复代码（不修改测试，除非测试本身有误）
  3. [Dev] 在测试报告中更新修复状态
  4. [QA] 重新运行测试，更新报告
```

**QA 报告格式**：
```
### [QA] 测试失败报告
- 失败用例: test_xxx
- 错误信息: AssertionError: ...
- 复现步骤: 1. ... 2. ...
- 疑似原因: ...（QA 的分析，供 Dev 参考）
```

**Dev 修复格式**：
```
### [Dev] Bug 修复
- 根因: ...
- 修复方式: 修改了 xxx
- 影响范围: 仅影响 xxx，不影响 yyy
```

> 🛑 **阶段四每轮循环完成 → 硬停止并主动 cascade 询问**
> 每轮修复或重测完成后，输出汇报并立即停止工作。主动使用 **cascade** 在对话中告知用户当前进度，并询问是否已切换到对应角色的模型、确认继续。**只有在用户明确回复确认后，才能进入下一轮或下一阶段**。

---

### 阶段五：交叉审查（Dev ↔ QA 互查）

> ⚠️ **交叉审查必须按角色使用对应模型**
> - QA 审查 Dev 代码时，当前模型必须为 **SWE-1.7 Max**
> - Dev 审查 QA 测试时，当前模型必须为 **GLM-5.2 High**
> 阶段开始前，你必须先使用 **cascade** 在对话中主动询问用户确认当前模型已切换到对应角色所需模型；确认后方可继续。

1. **QA 审查 Dev 的代码**（用 SWE-1.7 Max 的实现视角）：
   - 配置值是否从 TOML 读取（未硬编码）
   - 双环境隔离规则是否遵守
   - 是否有潜在的性能问题或资源泄漏
   - 是否破坏了已有功能

2. **Dev 审查 QA 的测试**（用 GLM-5.2 High 的逻辑视角）：
   - 测试是否可独立运行
   - 是否遵循现有测试风格
   - 是否有遗漏的边界场景
   - mock/fixture 是否合理

**审查输出**：
```
## 交叉审查结果
### [QA → Dev] 代码审查
- ✅ 配置从 TOML 读取
- ⚠️ xxx 函数缺少错误处理
### [Dev → QA] 测试审查
- ✅ 测试可独立运行
- ⚠️ 缺少 xxx 边界场景的测试
### 审查结论
- 需修复项: N
- 已修复: N
```

> 🛑 **阶段五完成 → 硬停止并主动 cascade 询问**
> 输出审查结果后，立即停止工作。主动使用 **cascade** 在对话中告知用户：
> "阶段五（交叉审查）已完成。接下来进入阶段六（总结报告），请确认后继续。"
> 并询问用户是否已切换并确认，**只有在用户明确回复确认后，才能继续**。未得到确认前不得继续，**不要自行进入阶段六**。

---

### 阶段六：总结报告

**输出格式**：
```
## 协作总结

### 变更清单
| 文件 | 类型 | 作者 |
|------|------|------|
| `src/...` | 新增/修改 | Dev |
| `tests/...` | 新增/修改 | QA |

### 验证命令
```bash
uv run pytest tests/unit/ -v
```

### 遗留问题
- 无 / 列出未解决项
```

## 协作规则

1. **职责隔离**：Dev 不写测试，QA 不写业务代码（Bug 修复循环中 Dev 只改业务代码）。**每个阶段完成后必须硬停止并主动使用 cascade 在对话中询问用户确认模型**，禁止跨阶段连续执行，必须等用户通过 **cascade** 明确确认后，由新一轮对话继续下一阶段
2. **模型匹配**：每个阶段开头，你必须先使用 **cascade** 在对话中主动询问用户当前模型是否已切换到对应角色所需的基座模型，确认后方可继续
3. **模型隔离**：**严禁 Dev、QA 使用同一基座模型工作**。Dev 的所有工作必须使用 **GLM-5.2 High**，QA 的所有工作必须使用 **SWE-1.7 Max**。每次角色切换时，你必须使用 **cascade** 在对话中主动询问用户确认已切换到目标模型，确认后方可继续
4. **评审报告**：阶段一每次评审/复核后，必须按进度输出/更新评审报告到 `docs/review_reports/YYYY-MM-DD_<主题>.md`；下一轮 Dev/QA 在继续前必须阅读该报告
5. **阶段间模型确认**：Dev 当前阶段工作完成后，你必须使用 **cascade** 在对话中主动询问用户确认模型，并按流程（Dev 或 QA）告知下一步所需模型；用户切换并明确确认后，由新一轮对话继续后续工作
6. **沟通格式**：跨角色沟通时标注 `[Dev]` 或 `[QA]` 前缀
7. **阶段汇报**：每个阶段完成后简要汇报，用户确认后进入下一阶段
8. **遵循规范**：所有产出遵循 `.windsurfrules` 中的项目规范
9. **不跳测试**：不删除或弱化已有测试，不跳过失败的测试
10. **双向输出**：QA 每次测试工作完成后必须输出报告到 `docs/test_reports/`，Dev 开工前必须查阅；Dev 每次开发完成后必须输出变更日志到 `docs/change_logs/`，QA 开工前必须查阅
