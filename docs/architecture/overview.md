# 架构总览

## 一句话概括

GameBot 是KK对战平台下的War3、y3等游戏的 Python 自动化脚本系统，通过大漠插件 COM 控制游戏窗口，结合 OCR/AI 推理识别游戏状态，自动完成KK对战平台下的游戏的日常、周常等任务（包括游戏里的局内、KK上的局外任务），并提供 Web 可视化配置端。

## 分层架构

系统从下到上分为六层，每层只依赖下层，不反向依赖：

> 注：以下为**逻辑分层**，路径标注仅作索引。物理上 `runner/` 包含其中四层
> （`business/`、`driver/`、`tasks/`、`team/`）外加 `runner/ui/`（浮窗）与
> `runner/resource_manager.py`；`inference/`、`dm_bridge/`、`config/`、`utils/`、`web/`
> 为顶层包。

```
┌─────────────────────────────────────────────────────────┐
│  Web 配置端        │ 可视化配置 + 任务启动面板            │
│  (web/)            │ FastAPI + Vue 3                      │
├─────────────────────────────────────────────────────────┤
│  任务编排层        │ 任务流程编排、循环控制、浮窗进度展示  │
│  (runner/tasks/ +  │ 基类 + 原子任务 + 各类具体任务       │
│   runner/ui/)      │ runner/ui 为浮窗（tkinter）          │
├─────────────────────────────────────────────────────────┤
│  业务逻辑层        │ 游戏内操作的原语化封装                │
│  (runner/business/)│ KK平台 → War3通用 → 九种兵器2        │
├─────────────────────────────────────────────────────────┤
│  组队框架          │ 多开协作（可选，独立于单开任务）      │
│  (runner/team/)    │ 编排器 + 队长/队员 + 文件IPC          │
├─────────────────────────────────────────────────────────┤
│  驱动层 + 推理     │ 大漠COM桥接 / OCR / AI检测            │
│  (runner/driver/ + │ 主环境3.12 ←RPC→ 子进程3.8(大漠)     │
│   inference/ +     │ 推理在主环境进程内直接执行            │
│   dm_bridge/)      │                                      │
├─────────────────────────────────────────────────────────┤
│  配置 + 工具       │ TOML配置引擎 / 日志 / 异常 / 资源     │
│  (config/ + utils/)│ 全局单例，被所有上层使用              │
└─────────────────────────────────────────────────────────┘
```

### 各层职责

| 层 | 职责 | 关键特征 |
|----|------|----------|
| **配置+工具** | 加载合并TOML配置、统一日志、异常体系、资源路径管理 | 全局单例，无状态，被所有层依赖 |
| **驱动+推理** | 屏蔽大漠COM的32位限制、提供截图/找图/输入/OCR/AI能力 | 进程隔离（RPC桥接）、线程安全、模型懒加载 |
| **组队框架** | 多账号协作：建房/入房/同步退出/崩溃重启 | 独立进程模型、文件IPC、可选层 |
| **业务逻辑** | 把游戏操作封装为可复用的原语（移动/战斗/面板操作/场景导航） | 三级组合（KK→War3→九兵）、mixin+对象组合 |
| **任务编排** | 编排业务原语完成任务流程、循环控制、浮窗进度（`runner/ui/`） | 继承体系（基类→声望→具体）、统一入口模式 |
| **Web端** | 可视化配置编辑、任务一键启动 | 前后端分离、schema驱动表单、子进程启动任务 |

## 双环境隔离

这是本项目最核心的架构约束，源于大漠插件 COM 只支持 32 位 Python：

```
┌──────────────────────────┐     RPC（stdin/stdout 行式JSON）     ┌──────────────────────────┐
│  主环境 Python 3.12 (64位) │  ────────────────────────────────→  │  桥接子进程 Python 3.8 (32位) │
│  .venv                    │                                       │  .venv-dm                  │
│                            │  ←────────────────────────────────    │                            │
│  • Web服务器              │                                       │  • 大漠COM对象             │
│  • 全部业务逻辑           │                                       │  • COM调用串行执行          │
│  • OCR/AI推理（进程内）   │                                       │  • dm.dll注册管理          │
│  • 任务编排               │                                       │  • 仅依赖pywin32+loguru    │
│  • 配置引擎               │                                       │                            │
│  • 依赖: fastapi/rapidocr │                                       │  • 不装Web/OCR/AI依赖      │
│    /onnxruntime/numpy     │                                       │                            │
└──────────────────────────┘                                       └──────────────────────────┘
```

**设计理由**：
- 大漠插件是 Windows COM 库，只有 32 位版本，无法在 64 位 Python 中直接创建
- 主环境需要 64 位来运行 FastAPI、ONNXRuntime、RapidOCR 等现代库
- 通过子进程 RPC 桥接，让两个环境各司其职，互不干扰
- 每个大漠客户端实例独占一个桥接子进程，多开时互不干扰

**推理为什么在主环境进程内**：
- OCR（RapidOCR）和 AI（ONNXRuntime）都是 64 位库，在主环境直接调用
- 推理结果（文字、检测框）直接在主进程内存中传递，无需序列化开销
- `inference/worker.py` 既是一个可独立运行的 stdin/stdout JSON-RPC worker
  （`main()` 入口），也是底层实现函数库（letterbox / NMS / OCR / 检测 / 分类
  handler）。当前进程内客户端 `inference/local.py` 直接 import 复用其中的纯函数；
  `main()` 的子进程模式为备选方案，目前代码路径中无实际启动处，exe 打包同样走
  进程内 `LocalInferenceClient`。

## 数据流

### 单开任务的数据流

```
用户启动任务（CLI 或 Web）
  │
  ▼
配置引擎加载TOML → 合并依赖 → 生成配置闭包（dict）
  │
  ▼
任务类接收配置 → 构造业务对象（注入配置段）
  │
  ▼
业务对象通过驱动层操作游戏窗口
  │                          │
  ▼ 大漠操作（截图/输入）    ▼ 推理（OCR/AI）
  驱动层 → RPC → 桥接子进程   推理客户端（进程内）
  │         → 大漠COM          → RapidOCR/ONNX
  │
  ▼
任务循环：截图 → 识别状态 → 决策 → 输入 → 重复
  │
  ▼
浮窗显示进度 / 停止键中断
```

### 组队任务的数据流

```
用户启动组队任务
  │
  ▼
编排器进程（主控）
  │
  ├─ 启动队长子进程 ──→ 建房 → 广播房间号（文件IPC）
  ├─ 启动队员子进程 ──→ 轮询房间号 → 加入房间
  │
  │   文件IPC同步：房间号 / 游戏阶段 / 退出信号 / 进度
  │
  ▼
各成员独立执行游戏流程（准备→导航（任务初始点）→主任务→退出）
  │
  ▼
编排器汇总进度 → 浮窗展示 → 同步退出 → 下一局
```

## 关键设计决策

### 1. 配置依赖注入而非全局读取
任务入口调用一次 `load_task`，获得完整配置闭包，注入到任务类和业务对象。
业务代码不直接调用配置单例，避免隐式依赖、便于测试和隔离。

### 2. 业务层 mixin 组合而非继承树
War3Business 用 mixin 多继承组合「窗口管理 + 输入控制 + 技能控制 + 文字监测」能力，
而非用深层继承树。每个 mixin 职责单一，可独立测试。

### 3. 原子任务作为可复用单元
「走到NPC→接任务→沿路线行动→OCR检测完成→回NPC提交」抽象为原子任务
（`AtomicTaskBase`，子类只需指定 NPC 配置、行走偏移、技能格键名等少量类属性），
上层任务复用同一原子任务再做自身编排。例如「城门骚扰」是原子任务：
- **黑石城声望**（`reputation/blackstone_reputation.py`）复用它做次数循环——
  由 `ReputationTask` 按"声望上限 / 每次收益"反推需要完成的城门骚扰次数；
- **升级圣痕**（`others/upgrade_stigmata.py`）复用它做"拿机会→升级"交替循环——
  每完成一次城门骚扰获得一次圣痕升级机会，故编排成
  "城门骚扰 → 走到圣痕NPC → 升级一次 → 返回守卫队长"直至所有词条达标。

### 4. 文件 IPC 而非网络通信
组队框架用文件系统做进程间通信（原子写入 + 轮询读取），
而非 socket/消息队列。简单可靠，无需额外依赖，适合单机多开场景。

### 5. 推理进程内而非子进程
OCR/AI 推理在主环境进程内直接执行，避免子进程通信开销。
代价是主进程内存占用更大，但本场景推理量小，可接受。

## 入口体系

项目有三个并行入口，都通过配置引擎加载配置，但启动方式不同：

| 入口 | 用途 | 启动方式 |
|------|------|----------|
| `main.py` | CLI 运行单个任务 | `uv run python main.py fishing`（task 为位置参数，默认 fishing） |
| 任务模块 `__main__` | 直接运行特定任务 | `uv run python -m GameBot.runner.tasks...fishing` |
| Web 服务器 | 可视化配置 + 启动任务 | `uv run python -m GameBot.web.server` |

Web 端启动任务时，用 `subprocess.Popen` 启动任务模块子进程，与 CLI 入口独立。
两者都调用 `config.load_task` 加载配置，但路径推导逻辑不同。
