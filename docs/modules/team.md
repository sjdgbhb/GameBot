# 组队框架

> 源码位置：`src/GameBot/runner/team/` + `src/GameBot/runner/business/war3/jiubing2/team_steps_base.py`

## 职责

组队框架负责让多个账号/窗口协作完成一局游戏。它把「一个主控进程 + 多个子进程
（队长 + 若干队员）」组织起来，通过文件 IPC 完成房间号广播、准备状态同步、
游戏内退出同步以及进度上报。

这是项目中最复杂的模块，独立于单开任务体系，有自己的进程模型和通信机制。

## 对外能力

- **编排器**：启动并管理队长、队员子进程，汇总进度，监控崩溃重启
- **队长流程**：创建房间 → 广播房间号 → 等待队员准备 → 开始游戏
- **队员流程**：轮询房间号 → 加入房间 → 准备 → 等待游戏开始
- **成员基类**：通用的游戏内流程、进度上报、同步退出
- **步骤基类**：可插拔的四阶段流程（准备 → 初始位置 → 主任务 → 退出前动作）
- **九兵步骤实现**：九种兵器2 默认的准备阶段（选难度/选英雄/读档/装备/学技能）

## 依赖关系

- **配置系统**：加载组队任务配置和每个成员的任务配置
- **业务逻辑层**：KK业务（建房/入房）、War3业务（游戏内流程）、九兵业务（准备阶段）
- **驱动层**：大漠客户端（多开时每个成员独占一个桥接子进程）
- **共享工具**：日志、异常
- **UI层**：编排器浮窗（仅主控进程有浮窗，子进程无）

## 关键机制

### 进程模型
```
编排器进程（主控，有浮窗）
  ├── 队长子进程（python -m GameBot.runner.team.leader）
  ├── 队员子进程1（python -m GameBot.runner.team.follower）
  └── 队员子进程2（...）
```
- 编排器校验配置（一个队长、英雄不重复、目标玩家不重复）
- 用 `subprocess.Popen` 为每个成员启动子进程
- 编排器汇总各成员进度，更新浮窗

### 文件 IPC
组队框架用文件系统做进程间通信，位于 `logs/team_ipc/team_ipc_<session_id>/`：

| 文件 | 写入者 | 读取者 | 语义 |
|------|--------|--------|------|
| `room_info.json` | 队长 | 队员 | 房间号/密码/地图/局数 |
| `game_state.json` | 队长 | 队员 | 游戏阶段（如 in_game） |
| `exit_signal.json` | 同步源 | 其他成员 | 本局退出信号 |
| `stop_signal.json` | 编排器 | 所有成员 | 全局停止信号 |
| `progress/*.json` | 各成员 | 编排器 | 各成员进度上报 |

- 写文件用「先写 .tmp 再 os.replace」的原子写入
- 读文件用固定间隔轮询

### 同步退出
- 同步源（通常是队长）完成主任务后写 `exit_signal.json`
- 非同步源轮询该文件，收到后退出 War3
- 编排器在同步源崩溃时也会主动写 `exit_signal` 让其他成员回房

### 崩溃与重启策略
- **KK阶段**：任何子进程崩溃都直接重启
- **游戏阶段同步源崩溃**：写 exit_signal + 计数重启；超过 max_restart 则广播 stop_signal 停止全部
- **游戏阶段非同步源崩溃**：只告警，不影响其他玩家

### Flow 配置编排
每个成员在 TOML 中通过 `steps` 列表编排自己的流程：
1. `preparation` — 准备阶段（选难度/选英雄/读档/装备/学技能）
2. `xxx.position_init` — 进入任务起始位置
3. `xxx` 或 `xxx.run_task` — 主任务
4. `xxx.pre_exit` — 退出前动作（如存档）

任务模块定义步骤类继承九兵步骤基类，把实例方法绑定为模块级函数，
供成员基类通过动态 import 调用。

### 准备阶段职责分离
- 队长先选难度并广播 `game_state=in_game`
- 队员收到信号后再继续执行后续准备
- 随后统一执行准备阶段（选英雄/读档/圣痕/卡牌/神碎/学技能）

## 关键约束

### 多开绑定模式
- 单开用前台绑定（normal）
- 多开（成员数 > 1）自动切换到后台绑定（dx2截图 + windows3鼠标 + windows键盘）
- 后台绑定需要管理员权限
- dx2 模式要求窗口有一部分在屏幕外

### 窗口认领
- 多开场景下，每个成员需要认领属于自己的 KK 窗口和 War3 窗口
- 通过 OCR 玩家名匹配窗口归属
- 按 PID 串行化避免冲突

### 子进程无浮窗
- 只有编排器进程有浮窗（显示汇总进度）
- 队长/队员子进程无浮窗，通过文件 IPC 上报进度

## 配置约定

组队配置位于 `config/data/team/team_task.toml`：

| 配置项 | 语义 |
|--------|------|
| `members` | 成员列表，每个成员指定角色(leader/follower)、英雄、目标玩家、steps |
| `steps` | 成员的流程步骤列表（preparation/position_init/run_task/pre_exit） |
| `max_restart` | 同步源最大重启次数 |
| `sync_source` | 同步源角色（通常是 leader） |

## 禁忌

- ❌ 不要在子进程中使用浮窗（只有编排器有浮窗）
- ❌ 不要假设文件 IPC 读取一定成功（用轮询 + 超时处理）
- ❌ 不要让非同步源崩溃影响其他玩家（游戏阶段只告警）
- ❌ 不要忘记多开需要管理员权限（后台绑定模式要求）
