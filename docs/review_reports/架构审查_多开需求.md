## 三、本轮新发现问题

### 3.1 【P2】`_recover_round` 触发条件在 KK 失败重试时误升局号

- **位置**：`src/GameBot/runner/team/base.py` `run()` 第 178~179 行 `if self.get_role() == "leader" and self._current_round == 1: self._recover_round()`。
- **问题**：触发条件是 `_current_round == 1` 而非"进程启动后首次"。队长首局 KK 阶段失败（如建房失败）→ `continue` 回到循环顶部 → 此时自己已写入 `round=1` 的 progress（第 182 行 `_report_progress(state="kk_phase", round_num=1)`）→ `_recover_round` 读到 `max_round=1` → `_current_round = 2`。违背第 191 行"KK 阶段失败不递增局数"的设计意图。
- **影响**：队员靠 `info_round >= round_num` 语义收敛，无死锁，但局号漂移（跳号）、且 round=1 期间每次循环都重复读 IPC。
- **建议**：改为一次性标志（如 `_round_recovered`），仅进程启动后第一次循环执行。

### 3.2 【P2】`_report_progress` 节流可能吞掉关键状态转换，屏障退化为等满超时

- **位置**：`src/GameBot/runner/team/base.py` `_report_progress()` 第 676~677 行。
- **问题**：`state="in_game"` 且 `task_progress=""` 的上报受 `_progress_interval`（默认 2s）节流。若成员从 `game_phase` 上报到 `in_game` 上报的间隔 < 2s（加载极快或已在游戏中），`in_game` 状态永不落盘 → 队长屏障 `_wait_all_members_in_game` 看不到该成员 → 每局等满 `in_game_wait_timeout`（60s）降级。`run()` finally 中的 `stopped` 上报同理可能被吞，导致屏障的已停止跳过逻辑失效。
- **建议**：`state` 与上一次上报不同（状态转换）时绕过节流强制写入；节流仅作用于同状态的重复上报。

### 3.3 【P2】`_signal_watch_loop` 在 stop_event 置位期间自旋

- **位置**：`src/GameBot/runner/team/base.py` `_signal_watch_loop()` 第 494~518 行。
- **问题 1**：循环节拍用 `self.stop_event.wait(poll_interval)` 实现。restart/stop 信号置位 stop_event 后，`wait` 立即返回，在 `run()` 主循环处理并 `clear()` 之前（其间 `_safe_quit_game` 可能耗时数秒），watcher 以全速轮询信号文件（无间隔文件 I/O + CPU 自旋）。
- **问题 2**：同步源每轮都读取 restart_signal 文件并丢弃返回值（`is_sync_source` 不更新 `_last_restart_timestamp`），无害但每秒一次无效文件读。
- **建议**：节拍改用独立的 `threading.Event` 或 `time.sleep(poll_interval)`；`is_sync_source` 提前短路不读 restart_signal 文件。

### 3.4 【P3】杂项

- `_wait_all_members_in_game` 中 `now = time.time()` 在等待循环外只计算一次（第 550 行），等待期间死亡的成员不会转为 stale 判定；建议移入循环内。
- `test_team_ipc.py` `test_restart_signal` 仍在验证废弃的 `clear_restart_signal`，未覆盖 `min_timestamp` 纪元语义（归入上轮 3.10 测试欠账）。
- `follower.kk_phase` 第 0 步 `_claim_hall_window()` 失败时静默降级 `owner_pid=0`，全链路 PID 过滤随之失效。docstring 已声明该回退，建议多开场景（members 数 > 1）下升级为 error 日志便于排查。
