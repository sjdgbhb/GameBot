### 1.3 现有架构约束

- **双环境隔离**：所有大漠 COM 脚本运行在 `.venv-dm`（32 位 Python 3.8），IPC 机制必须兼容 3.8。
- **单进程 DmClient**：`DmClient` 是全局 COM 对象，每个进程独立创建，不可跨进程共享。
- **配置继承机制**：`load_task` 通过 `name` 和 `extends` 声明继承链，深度优先后序展开，英雄互斥生效。
- **Web 启动方式**：`services.py` → `start_task` 通过 `subprocess.Popen` 拉起任务子进程，从 `base.toml [main].python_path` 读取 3.8 Python 路径。

## 二、无尽任务优化技术方案

### 2.1 功能点 1：BOSS 死亡提示超时处理

**改动文件**：
- `src/GameBot/runner/business/war3/jiubing2/endless_runner.py` — `_wait_boss_dead()`、新增 `BossDeathTimeoutError`
- `src/GameBot/runner/tasks/war3/jiubing2/endless/endless.py` — `do_war3()` 新增异常捕获
- `src/GameBot/runner/tasks/war3/jiubing2/endless/endless_single.py` — 新增异常捕获
- `src/GameBot/runner/dm_client.py` — `save_screenshot` 新增 `force` 参数

**方案**：

修改 `_wait_boss_dead()` 方法，超时后：
1. 保存当前屏幕截图（`save_screenshot(label="boss_death_timeout", force=True)` 绕过 1 秒频率限制）
2. 抛出 `BossDeathTimeoutError`，让上层捕获后处理

**行为区分**：
- **组队模式**：按组队同步规则处理（同步源广播 `exit_signal.json`，非同步源等待退出信号）
- **非组队模式**：单局无尽停止任务，多局无尽正常退出 War3 继续下一局

`endless.py` 和 `endless_single.py` 中异常捕获在 `with dm.bind_window` 块外，`quit_game` 自行绑定窗口后退出。

**行为变更**：任何一层 BOSS 死亡超时都会触发截图（如退出则需遵循组队退出规则）。

### 2.2 功能点 2：退出游戏窗口存在性检查

**改动文件**：
- `src/GameBot/runner/business/war3/window_manager.py` — `quit_game()`
- `src/GameBot/runner/dm_client.py` — 新增 `get_bind_window()`

**方案**：

`quit_game` 执行退出逻辑前：
1. `_find_war3_hwnd()` 检查窗口是否存在，不存在则保存当前屏幕截图、记录 warning 并返回。
2. `get_bind_window()` 检测当前绑定状态：
   - 已绑定同一窗口 → 直接发送 F10→E→Q，不重复绑定。
   - 未绑定或绑定了其他窗口 → 自行 `bind_window` 后发送按键。
3. `endless.py` 中 `quit_game` 统一移到 `with bind_window` 块外调用，避免嵌套绑定冲突。

### 2.3 功能点 3：KK 弹窗检测与关闭

**改动文件**：
- `src/GameBot/runner/business/kk/hall_manager.py` — 新增 `dismiss_hall_popups()`

**方案**：

`dismiss_hall_popups` 循环枚举 KK 类窗口，通过尺寸判断是否为弹窗：
- 受保护尺寸集合（大厅主界面、房间、创建房间弹窗、加入房间弹窗）不关闭。
- 小尺寸非受保护窗口通过 `close_window_by_x` 关闭。
- 每轮关闭一个弹窗后重新枚举（避免句柄失效），最多 10 轮防止无限循环。
- **必须在未绑定任何窗口的状态下调用**（`close_window_by_x` 内部会自行绑定弹窗）。
- **弹窗检测时机**：进入地图主界面（点击地图后，显示该地图主界面，其下方有创建房间按钮）、退出游戏后。
- `create_room` 中采用分段绑定策略：每步操作间退出绑定 → 清理弹窗 → 重新绑定。

### 2.4 功能点 4：KK 房间缺失时自动创建房间

**改动文件**：
- `src/GameBot/runner/business/kk/hall_manager.py` — 新增 `create_room()` 及辅助方法
- `src/GameBot/runner/tasks/war3/jiubing2/endless/endless.py` — 修改 `do_kk()`
- `src/GameBot/runner/dm_client.py` — 新增 `send_string()`
- `src/GameBot/config/data/kk.toml` — 新增 `[kk.create_room]` 配置段

**方案**：

`create_room` 流程（分段绑定策略）：
1. 查找 KK 大厅窗口 → `set_client_size`
2. 绑定大厅 → 点击搜索输入框 → `ctrl+a` 全选 → `delete` 清空 → `send_string(地图名, hwnd=hall_hwnd)` → 点击搜索图标
3. 等待搜索结果 → OCR 检测地图名（按 `(y_center, x_center)` 排序，取第一个匹配项）
5. 点击搜索结果 → 等待详情页 → 点击创建房间按钮
6. 等待创建房间弹窗 → 绑定弹窗 → 输入密码 → 点击创建 → 解绑
7. 等待房间窗口出现 → 绑定窗口 → 返回房间句柄

**关键问题处理**：
- 中文输入：`DmClient.send_string()` 封装 DmPlugin `SendString`，支持 Unicode，不依赖输入法。
- 组合键：使用 `key_press_char("ctrl+a")` 而非单独 `ctrl`。
- OCR 坐标：使用 `ocr_lines` 返回的 `x_center, y_center` 屏幕坐标点击。
- `do_kk` 修改：先检测已有房间，无房间时调用 `create_room`；`start_game` 新增 `room_hwnd` 参数避免重复检测。

### 2.5 功能点 5：多开目标窗口自动识别

**改动文件**：
- `src/GameBot/runner/dm_client.py` — 新增 `get_window_parent()`
- `src/GameBot/runner/business/kk/multi_instance.py` — `MultiInstanceMixin`
- `src/GameBot/runner/business/war3/window_manager.py` — 新增 `identify_war3_owner()`
- `src/GameBot/config/data/kk.toml` — 新增 `[kk.multi_instance]` 配置段
- `src/GameBot/config/data/war3/war3.toml` — 新增 `[war3.multi_instance]` 配置段
- `src/GameBot/config/data/war3/jiubing2/tasks/endless/endless.toml` — 新增 `target_player`

**方案**：

- **KK 大厅识别**（`identify_hall_owner`）：点击头像旁图标展开下拉框 → OCR 识别玩家 ID；多开下仅大厅需要 OCR 玩家名，房间/弹窗等其它窗口通过 PID + 尺寸/类名区分。
- **War3 识别**（`identify_war3_owner`）：通过加载页面玩家列表 OCR，返回排在最前面的玩家用户名。仅在加载页面有效，调用时机为 `wait_for_game_window` 后、`wait_enter_game` 前。
- **父子窗口辅助**（`check_parent_child_relation`）：`GetParent` 返回父窗口句柄，无父窗口返回 0。实测结论：KK 主界面与房间之间无父子关系，弹窗与主界面存在父子关系。多开区分主要依赖 PID + OCR。
- **目标窗口选择**（`_find_target_war3_hwnd`）：单窗口直接返回；多窗口时按 `target_player` 匹配 `identify_war3_owner` 结果。

#### 2.5.1 owner_pid / target_player 映射说明

| 字段 | 来源 | 含义 | 用途 |
|------|------|------|------|
| `target_player` | `team_task.toml` 中每个成员的 `target_player` | 该成员在 KK 大厅显示的玩家 ID，即主界面左上角头像下拉框中 OCR 识别到的名字 | 1. 由 `TeamOrchestrator` 校验唯一性；2. 作为 `sync_source` 的值；3. `claim_hall_window` 用它匹配大厅窗口；4. `identify_war3_owner` 用它匹配 War3 加载页玩家名 |
| `owner_pid` | 大漠 `get_window_process_id(hall_hwnd)` | 该成员 KK 主界面对应的 Windows 进程 PID | 1. 全流程窗口操作（`dismiss_hall_popups` / `dismiss_room_popups` / `create_room` / `join_room_by_id`）按 PID 过滤，避免误关/误操作其它 KK 实例；2. `TeamMemberBase` 缓存为 `self.hall_hwnd` / `self.owner_pid`，窗口失效时清空 |

**映射建立时序**：

```
TeamMemberBase._claim_hall_window()
    └─ HallManagerMixin.claim_hall_window(dm, target_player)
           ├─ 枚举尺寸等于 [kk.main.window_size] 的 KK 窗口
           ├─ 取每个候选窗口的 PID
           ├─ 恢复最小化、set_client_size、清弹窗
           └─ MultiInstanceMixin.identify_hall_owner(dm, hwnd) → OCR 玩家名
           └─ 玩家名 == target_player 时返回 (hall_hwnd, owner_pid)
```

**多开约束**：

1. **仅大厅 OCR 一次玩家名**（`identify_hall_owner`）。房间、弹窗、War3 加载页等其它窗口不用于建立 `target_player → owner_pid` 映射，仅通过 `owner_pid` 过滤。
2. **弹窗归属判定**：`dismiss_hall_popups` 枚举同 `window_class` 的窗口时，用 `owner_pid` 过滤；`dismiss_room_popups` 同理。
3. **缓存与失效**：`TeamMemberBase._claim_hall_window` 会缓存 `(hall_hwnd, owner_pid)`。若窗口仍在且 PID 未变，则每局复用；若窗口消失或 PID 改变，清空缓存并重新 OCR 认领。
4. **唯一性**：`TeamOrchestrator` 在启动时校验 `members` 中所有 `target_player` 唯一，防止多开子进程争夺同一名称。

## 三、通用组队任务框架技术方案

### 3.1 IPC 机制选型

**方案：基于文件的轻量 IPC（JSON + 原子写入）**

```
logs/team_ipc/team_ipc_<session_id>/
├── room_info.json          # 队长广播：{ room_id, password, map_name, round, timestamp }
├── game_state.json         # 游戏状态广播：{ phase, sync_source, round, timestamp }
├── exit_signal.json        # 退出信号：{ round, reason, timestamp }
├── stop_signal.json        # 全局停止信号
├── restart_signal.json     # 同步源重启信号
└── progress/               # 各成员任务进度（供入口浮窗汇总展示）
    ├── leader.json         #   { member_name, task_name, task_progress, round, timestamp }
    ├── follower_0.json
    └── follower_1.json
```

**设计细节**：
- **写入**：原子写入（先写 `.tmp` 再 `os.replace`），避免读取到半写内容。
- **轮询**：队员每 0.5s 轮询 `room_info.json`，检测 `timestamp` 变化判断新局开始。
- **进度上报**：各子进程每 2s 写入自身 `progress/<role>.json`，入口进程读取后汇总显示在浮窗。`task_progress` 由具体任务产出（如 `endless` 输出 `round=3/10`，`fishing` 输出 `caught=5/20`）。
- **会话 ID**：由入口进程启动时生成（时间戳+PID），通过环境变量 `TEAM_SESSION_ID` 传递给所有子进程。
- **无外部依赖**：仅用 `os`、`json`、`time`，兼容 Python 3.8 32 位。
- **准备状态**：不通过 IPC 上报，队长直接 OCR 识别房间内各楼层玩家状态。

**性能说明**：单条 JSON < 500 字节，`os.replace` 在 SSD 上约 0.1~1ms，远低于秒级同步精度要求。并发子进程数 ≤ 8 无压力。

### 3.2 进程架构

```
team_task.py（入口进程，3.8 环境）
  │
  ├── 读取 team_task.toml 配置
  ├── 生成 session_id
  ├── TeamOrchestrator
  │     ├── subprocess.Popen → leader.py（队长子进程）
  │     ├── subprocess.Popen → follower.py（队员1子进程）
  │     ├── subprocess.Popen → follower.py（队员2子进程）
  │     └── ...
  │
  └── 监控所有子进程状态，同步源崩溃时重启，非同步源崩溃仅告警
```

**子进程启动方式**：
- 从 `base.toml [main].python_path` 读取 3.8 Python 路径。
- 通过环境变量传递角色信息：`TEAM_ROLE`、`TEAM_SESSION_ID`、`TEAM_MEMBER_INDEX`、`TEAM_CONFIG_PATH`。
- 子进程通过 `config.load_task("team.team_task")` 加载完整配置，再根据 `TEAM_MEMBER_INDEX` 提取自身成员配置。

### 3.3 队长流程

```
Leader.run()
  │
  ├── 1. 识别自身 KK 大厅窗口（identify_hall_owner）
  ├── 2. 清理弹窗 → create_room（复用 HallManagerMixin）
  ├── 3. OCR 读取房间左上角房间号
  ├── 4. 广播 room_info.json（room_id + password + map_name）
  ├── 5. OCR 轮询房间内所有 player_id 出现状态，等待所有队员准备完成（超时可配置；超时则重建房）
  ├── 6. start_game（复用 RoomManagerMixin）
  ├── 7. 等待 War3 窗口 → 绑定 → select_difficulty
  ├── 8. 广播 game_state.json（phase=in_game）
  ├── 9. 执行队长配置的 flow（preparation → position_init → task_module → pre_exit）
  ├── 10. 同步逻辑：
  │      ├── 若队长是同步源：任务完成/失败时广播 exit_signal.json
  │      └── 若队长非同步源：监听 exit_signal.json，收到后停止当前任务
  ├── 11. quit_game
  └── 12. 循环：回到房间（步骤 5），若房间已意外退出则重建房（步骤 2）并广播新 room_info.json
```

### 3.4 队员流程

```
Follower.run()
  │
  ├── 1. 识别自身 KK 大厅窗口（identify_hall_owner）
  ├── 2. 轮询 room_info.json，收到房间信息
  ├── 3. JoinRoomById（新模块）
  │      ├── 搜索地图名 → 进入地图详情页
  │      ├── 点击"房间列表"按钮
  │      ├── 输入房间号 → 点击搜索
  │      ├── 双击搜索结果
  │      ├── 输入密码 → 确认
  │      └── 入房失败：写 progress 上报 join_failed，等待队长广播新 room_info.json
  ├── 4. 点击"准备"按钮
  ├── 5. 等待 War3 窗口 → 绑定（identify_war3_owner 匹配 target_player）
  ├── 6. 等待 game_state.json（phase=in_game，表示队长已选完难度）
  ├── 7. 执行 flow 编排（preparation → position_init → task_module → pre_exit）
  ├── 8. 同步逻辑：
  │      ├── 若队员是同步源：任务完成/失败时广播 exit_signal.json
  │      └── 若队员非同步源：监听 exit_signal.json，收到后停止当前任务
  ├── 9. quit_game
  └── 10. 循环：回到房间（步骤4），若自身不在房间，则从步骤2开始重新执行
```

### 3.5 同步源机制

- 同步源由用户在 `team_task.toml` 中通过 `sync.sync_source` 显式指定（`target_player`，默认队长）。
- 入口进程读取配置，将 `sync_source` 通过 `game_state.json` 广播。
- 各成员按 `game_state.json` 中的 `sync_source` 判断自身角色。
- 同步源成员完成/失败时，写 `exit_signal.json` 触发全队退出。
- 队长收到 `exit_signal.json` 后执行退出，回到房间或重建房，开始下一局。
- 所有任务均为单局任务，由组队框架负责循环下一局。

### 3.7 流程编排（flow）

每个成员通过 `flow` 配置编排游戏内流程，四阶段：

### 5.1 队长崩溃退化路径

队长进程是组队流程的核心驱动者，崩溃后需保证队员不死锁、不无限等待。

**退化机制**：
1. **Orchestrator 监控**：`TeamOrchestrator._monitor_loop` 检测到队长进程异常退出（`poll() != 0`）时，若队长是同步源则广播 `restart_signal` 并重启队长子进程（受 `max_restart` 限制）；若队长非同步源则仅告警。
2. **队长重启后恢复**：`_recover_round` 从 IPC 中读取所有成员已记录的最大 `round`，以 `max_round + 1` 开始，避免重复已完成的局。
3. **队员侧收敛**：队员通过 `room_info.json` 的 `timestamp` 纪元判断新局，队长重启后广播的新 `room_info` 携带新 `timestamp`，队员自动收敛到新局。
4. **屏障退化**：`_wait_all_members_in_game` 对 `state=stopped` 或 `timestamp` 过期（3×timeout）的成员自动跳过，避免队长重启后因死亡成员阻塞屏障。
5. **重启超限**：队长重启次数超过 `max_restart` 后，Orchestrator 广播 `stop_signal` 停止全部成员。

**限制**：
- 队长崩溃期间已进入游戏的队员无法退出（依赖 `exit_signal`），需等待队长重启后广播退出信号，或队员自身 `_sync_exit` 超时后自行退出。
- 队长崩溃时若正在建房，可能产生孤立房间，队员通过 `room_info` 的 `timestamp` 纪元自动忽略旧房间信息。

### 5.2 绑定模式与输入竞争

多开场景下每个子进程独立创建 `DmClient` COM 对象，通过 `bind_window` 绑定各自的游戏窗口。大漠插件支持多种绑定模式，不同模式对后台操作和输入竞争的行为不同。

**绑定模式说明**：

| 绑定模式 | 后台操作 | 输入竞争 | 适用场景 |
|----------|---------|---------|----------|
| 前台（`normal`） | ❌ 需窗口在前台 | ✅ 多窗口冲突 | 单开或调试 |
| 后台 GDI（`gdi` / `gdi2`） | ✅ 图色后台 | ❌ 按键仍走前台 | KK 大厅操作 |
| 后台 Windows（`windows3`） | ✅ 图色+按键后台 | ✅ 各窗口独立 | War3 游戏内操作（待验证） |
| DirectX（`dx` 系列） | ✅ 图色+按键后台 | ✅ 各窗口独立 | War3 游戏内操作（待验证） |

**当前实现**：
- KK 大厅阶段：使用 `gdi` / `gdi2` + `windows3` + `windows` 组合，支持后台图色截图和后台按键。
- War3 游戏阶段：使用 `dx` 系列绑定，支持后台图色和后台按键。
- **OCR 截图**：当前仍使用 `ImageGrab.grab(bbox)` 屏幕截图（前台），**未走大漠绑定通道**。这是后台化的前置短板：多成员游戏内并发上线需 OCR 改为大漠侧 `GetScreenData` / `CapturePre` 截图存盘 + 推理子进程读图文件。

**输入竞争风险**：
- 前台绑定模式下，多个子进程的键盘/鼠标操作会互相干扰（`SendString` / `key_press` 发送到前台窗口）。
- 后台绑定模式下，各子进程通过 `hwnd` 定向发送输入，理论上无竞争。但 `dx` 系列绑定在部分 War3 版本上可能失效（需逐组合真实验证）。
- **分段绑定策略**：`create_room` 和 `join_room_by_id` 中每步操作间退出绑定 → 清理弹窗 → 重新绑定，避免嵌套绑定冲突。

**待验证项（P0 前置）**：
- KK 绑定模式 `gdi` / `gdi2` + `windows3` + `windows` 逐组合真实验证。
- War3 绑定模式 `dx` 系列逐组合真实验证。
- OCR 截图改为大漠侧截图存盘 + 推理子进程读图文件。
- **多成员游戏内并发上线条件：上述 spike 通过前不具备。**

## 六、关键设计决策

1. **IPC 机制**：文件 IPC（JSON 原子写入 + 轮询），无外部依赖，兼容 3.8 32 位环境，调试友好。
2. **房间号获取**：房间窗口左上角 OCR 读取。
3. **准备状态确认**：队长 OCR 识别房间内各楼层状态，不通过 IPC 上报。
4. **同步源配置**：由用户显式指定，运行时不再动态选取。
5. **多局/单局区分**：已移除，所有任务均为单局任务，框架负责循环。
6. **浮窗方案**：仅入口进程有浮窗，显示任务进度（`task_progress`），脚本流程状态仅用于调试。
7. **中文输入**：`DmClient.send_string()` 封装 DmPlugin `SendString`，不依赖输入法状态。
8. **`quit_game` 调用位置**：统一在 `with bind_window` 块外调用，通过 `get_bind_window()` 防嵌套绑定。
9. **`create_room` 分段绑定**：每步操作间退出绑定 → 清理弹窗 → 重新绑定，避免嵌套绑定冲突。
10. **OCR 搜索结果排序**：按 `(y_center, x_center)` 排序，确保"从左至右、从上至下"。
11. **队长崩溃退化**：Orchestrator 检测队长异常退出后广播 `restart_signal` 并重启（受 `max_restart` 限制）；队长重启后通过 `_recover_round` 从 IPC 恢复局号；队员通过 `room_info` timestamp 纪元自动收敛到新局。
12. **绑定模式与输入竞争**：KK 阶段使用后台 GDI 绑定，War3 阶段使用 `dx` 系列后台绑定，各子进程通过 `hwnd` 定向发送输入避免竞争。OCR 截图当前仍走 `ImageGrab` 屏幕截图，改为大漠侧截图存盘是后台化前置条件。
