# 技术方案 — 配置系统重构（TOML 纯文件方案）

> 状态：设计稿（未实施）
> 范围：`src/GameBot/config/` 引擎 + `config/data/` 全部 TOML + 业务层取配置方式
> 前置约束：**不做可视化配置端、不引入数据库、不换配置引擎**，在现有引擎上收紧与显式化。

## 1. 现状诊断

`load_task` 产出的 merged config（见 `merged_cfg_endless_善木木.json`，1740 行）暴露了以下问题：

| 问题 | 表现 |
|---|---|
| 来源丢失 | 合并成扁平 dict 后无法回答"这个值是哪个文件写的" |
| 派生数据混入 | `war3.bind` 是 `bind_background` 的拷贝；`hero.inventory_slots` 是 `kk.inventory_slots` 的注入拷贝；`bind_mode` 源字段派生后成死数据 |
| 隐式规则 | ~~命名空间根靠扫描 `data/` 一级目录推导~~ 已改为显式注册表；~~裸键共享区~~ 已废弃，裸键归入各自命名空间 |
| `[this]` 不继承 | 各文件 `[this]` 落在各自路径（兄弟共存），"变体覆盖基任务"目前靠业务代码手动合并（`endless.py:42-52`、`ingame_special.py:26-32`） |
| 编排覆盖靠约定 | `ingame_special` 的 `[this.fishing]` 靠 `_apply_overrides` 硬编码搬运到 `tasks.others.fishing`，TOML 读者无从得知 |
| 无校验 | 键名打错静默合并出死数据；类型错了运行时才炸 |
| 用户覆盖双轨 | 变体 TOML 与 `user_configs.json`（含 `user.py` 硬编码路由表）功能重叠 |

## 2. 设计原则

1. **意图写在配置里，不藏在代码里**——所有"这段配置给谁用"必须由 TOML 语法本身表达
2. **作者只需要三种寻址写法**——`this` / 裸键 / 绝对路径，其余规则由位置和键名自动决定
3. **字典里只有人写过的数据**——派生值（bind 选择、格子注入、物品名解析）一律访问器即时计算
4. **每个值可查来源**——合并时记录 provenance，提供 `explain`/`dump --annotate`
5. **分阶段迁移，无不可用窗口期**——每步独立交付、行为等价优先

## 3. 目标架构

### 3.1 分层模型（显式声明 + 引擎校验）

```
L0 base      base.toml                        应用基础设施（路径/大漠/推理/浮窗）
L1 platform  war3/war3.toml, kk.toml, web.toml, team/*    平台窗口与绑定
L2 domain    war3/jiubing2/jiubing2.toml      游戏机制（指令/物品/UI几何）
L3 hero      war3/jiubing2/heroes/*.toml      英雄（互斥组）
L4 scene     war3/jiubing2/scenes/*.toml      场景
L5 task      war3/jiubing2/tasks/**/*.toml    任务与变体
L6 user      user_configs.json（可选，机器本地覆盖）
```

**extends 方向约束（resolver 校验，违反即 `ConfigurationError`）：**

- 低层文件（L0~L4）不得 extends `tasks.*`
- **task→task 允许任意引用**（`daily_reputation→atomic.*`、`endless→endless_single`、变体→基任务，均为既有用法），循环由 DFS 检测
- 变体约定：`<基任务>_<后缀>.toml` 与基任务同目录，只 extends 基任务

**命名空间根改为显式注册表**（替代目录扫描）：

```python
NAMESPACE_ROOTS = frozenset({"war3", "kk", "web", "team", "base"})
```

新增任务/英雄/场景/变体文件**不需要改注册表**（都在 `war3` 根内）；只有新增一级命名空间才加一行——这本就该是显式决策。扫描模式的风险：`data/` 下任何新建目录都会把同名裸键从"可继承"翻转为"命名空间隔离"，无报错、静默改变行为。

### 3.2 三种寻址写法（作者唯一要懂的规则）

```toml
[this.xxx]                          # 相对寻址：落在自己文件的命名空间路径下
[war3.jiubing2.tasks.others.fishing] # 绝对寻址：直接打到指定节点（放开旧格式禁令，深度≥2）
[hero]                              # 顶层特例：局内唯一英雄，任务层横向覆盖英雄层
```

| 写法 | 落点 | 同名时 | 典型用途 |
|---|---|---|---|
| `[this.x]` | 自己文件路径下 | 兄弟共存（防冲突） | 任务参数、平台设置 |
| `[hero]` | 顶层 | 浅合并子键（英雄互斥） | 英雄配置、任务覆盖英雄子键 |
| `[完整路径]` | 指定节点 | 覆盖目标节点同名字段 | 编排任务调子任务参数 |

判断口诀：**同名会冲突 → `this`；给闭包里别的节点打补丁 → 写全路径。**

- `this` 与全路径在引擎内统一为同一管线：`this` 展开为绝对路径后与手写绝对路径走同一个命名空间深合并，代码反而简化。
- `_reject_old_namespace_sections` 只拦截**自身文件写自身命名空间根**（如 `war3.toml` 写 `[war3]`）防旧格式回潮；**跨层覆盖放行**——任何文件都可以写 `[war3.xxx]`/`[kk.xxx]`/`[war3.jiubing2.tasks.others.fishing]` 等绝对路径对闭包内其他节点打补丁。lint 校验目标路径在闭包内存在。
- 顶层只有一个特殊键：`hero`（局内唯一英雄，任务层横向覆盖英雄层的通道）。其余配置全部归属命名空间节点（`base.xxx`/`war3.xxx`/`kk.xxx`/`war3.jiubing2.xxx`），旧的"裸键共享区"已废弃——裸键不再提升到顶层，请用 `[this.xxx]` 归入自身命名空间。`result["_extends"]` 记录各配置文件的 extends 依赖映射，供 `get_task_view` 沿链合并任务视图。

### 3.3 任务视图 → `get_task_view(cfg, task_name)`

`load_task` 不再预合并 `result["task"]`，而是在结果中存储 `result["_extends"]` 映射。
业务代码通过 `get_task_view(cfg, task_name)` 按需沿 extends 链深合并任务视图：

```
load_task("…endless_善木木") 的 extends 链：
endless_single [this] → endless [this] → endless_善木木 [this]  ─get_task_view→  合并视图
```

- 变体 `[this].min_level` 覆盖基任务（标量覆盖）；`[[this.points]]` 整表替换
- 变体不写的参数自动从基任务继承；要覆盖则写全路径打到基任务节点
- 业务代码统一 `get_task_view(cfg, task_name)["points"]`，不再依赖 `cfg["task"]` 别名
- `cfg["war3"]["jiubing2"]["tasks"]` 原始树保留（编排任务仍需按名字空间取子任务段）

### 3.4 编排任务的子任务覆盖（绝对寻址替代 `_apply_overrides`）

```toml
# ingame_special.toml —— 写法即语义，不再依赖代码搬运约定
[war3.jiubing2.tasks.others.fishing]
max_times = 40

[war3.jiubing2.tasks.reputation.daily_reputation]
enable_blackstone = true
```

`target_player` 透传子任务（`ingame_special.py:56-61` 手动写两个节点）同样收编：引擎规则"任务 `[this]` 的 `target_player` 自动下发到 extends 闭包内所有 `tasks.*` 节点中未自设该键者"，或编排任务用绝对寻址显式写。倾向后者——少一条魔法规则。

### 3.5 派生值访问器（字典不再含拷贝）

```python
config.bind_for("war3")            # 读 bind_mode/target_player → 返回 bind_foreground/background + bind_mode
config.get_inventory_slots(hero)   # hero.inventory_slots 缺省回落 kk.inventory_slots
```

- `war3.bind`、`kk.bind`、`hero.inventory_slots` 不再写入配置字典
- `war3.bind_mode` 保留为源字段（业务侧判断前后台用）
- 物品名→`item_id` 解析保留，语义记为"编译期符号解析"（物品表从 `war3.jiubing2.items` 读取）
- **用户改配置方式不变**：改 `bind_mode`/`bind_background.*`/`kk.inventory_slots`/`hero.inventory` 等源字段

### 3.6 provenance 与工具

`_build` 深合并时并行记录 `provenance: {dot_path → source_config_name}`（记到子键粒度，如 `hero.shard`、`tasks.*.points`），不进结果字典。

```bash
python -m GameBot.config explain <task> <dot.path>   # 某键来源：文件 + 被谁覆盖
python -m GameBot.config dump <task> [--annotate]    # 有效配置导出（可带来源标注），替代手写 merged_cfg
python -m GameBot.config lint                      # 全量校验
python -m GameBot.config new task others.xxx --hero hxd   # 脚手架生成骨架
python -m GameBot.config new variant endless.endless --player 李四
```

**lint 检查项：**

- extends 方向违规（低层引 tasks.*）、循环依赖
- 裸键名撞命名空间根（保留现有拦截）
- 任务文件写了疑似应为 `this` 的裸键（如 `[points]`）→ 提示
- 绝对寻址目标路径在闭包内不存在 → 报错
- `[hero.xxx]` 子键字段不全（浅合并整表覆盖，易漏字段）→ 警告
- 危险字段标记（`absorb_index` 等）→ 确认提示
- 未知键警告：为 hero/war3/kk/任务节点维护"已知键清单"，挡住打错字的静默合并

### 3.7 用户覆盖收敛为单轨

现状双轨：变体 TOML（git 内共享）+ `user_configs.json`（机器本地，`user.py` 硬编码路由）。收敛方案：

- **变体 TOML 是唯一的"玩家档案"机制**（`<任务>_<玩家>.toml`）
- `user_configs.json` 若仍用于机器本地覆盖：保留但把 `user.py` 的 if-else 路由改为声明式映射表 `{user_key: (目标dot路径, merge_mode)}`，特判（`blackstone_points` 等）入表；英雄替换（`hero` 字段→换 heroes.* 依赖）保留为组合期行为
- 若确认无实际使用 → 整体删除 `user.py`，少一条规则

## 4. 保留不动的语义

- DFS 后序线性化、每文件加载一次、后到覆盖先到
- `[hero]` 浅合并（子键整表覆盖）、`heroes.*` 互斥；`hero` 是唯一保留顶层的配置键
- `[this]` 展开 = 文件路径推导名；`get_task_view(cfg, task_name)` = 沿 extends 链深合并任务视图（按需调用，不预存 `cfg["task"]`）
- TOML 无法表达"删除键/数组元素级操作"：功能开关一律用 `enable_xxx = false`（如 `ingame_special` 变体关钓鱼），不删配置

## 6. 明确不做的事

- **不换引擎**（Hydra/Dynaconf）：痛点不在合并算法；领域语义（英雄互斥、this、浅合并）迁移成本高
- **不上数据库**：配置与代码强耦合（坐标跟客户端版本走），git 提供历史/diff/blame/评审；DB 解决的是并发写与查询，本场景没有
- **不做全量可视化**：如未来重启 web 端，只收缩为"玩家档案编辑器"（schema 渲染表单 + tomlkit 写回 + provenance 展示继承）；本设计的 provenance/校验届时可直接复用
